# 云域统一采购、商签通按企业付费分配签署份数

> 后续已按官方“平台统一发起、真实双方签署”方案完成代码实现，部署、迁移、配置与旧任务恢复要求见[上线说明](platform-initiated-signing-release-2026-10-24.md)。下文保留方案核查时的需求与能力分析。

## 已确认的业务要求

云域向法大大统一采购签署用量。其他企业在商签通购买套餐或签署包，由平台给对应企业发放购买的签署份数。企业不需要再到法大大重复购买。

例如，A 企业购买 10 份、B 企业购买 30 份，两家分别取得 10 份和 30 份权益；云域提供底层签署用量。A 的消费不能占用 B 的已购权益。重复支付回调不重复发放，同一合同版本不重复扣量，后续续购按订单份数增加。

“注册企业”“实名授权企业”“已付款且还有有效份数的企业”是不同状态。不能将所有已授权企业默认设为无限消耗云域套餐，也不能把商签通账本增加 N 份当作法大大已成功共享 N 份。

## 现有实现及缺口

- `MembershipPurchaseService.settle` 通过可信支付回调或查单，匹配订单、付款人、商户、金额和状态，事务内建立 `PAID:订单号` 的企业额度池，重复回调不会重复发放。
- `MembershipService` 按认证主体区分权益、有效期和份数，发起签署时预占，取得服务商任务后确认消费，结果不明保留预占等待核对。
- 本地支付和额度链路没有执行法大大共享开通或份数分配。当前代码没有证据保证“本地已到账”同时表示“服务商共享已生效”。这正是需要打通的交付缺口。
- 法大大 `212010` 只证明本次发起企业的可用量不足，不能证明云域采购的总量耗尽。用户提示已改为联系平台核对共享配置，不再直接要求补购。

## 法大大公开能力边界

已检查项目固定 Java SDK `5.8.7.0428.3`、官方 SDK 页面指向的最新 `5.8.7.0428.6` 及 5.1 公开计费文档。计费 API 提供订阅、余量、账单和订单等只读查询，未找到可按企业新增、增加、修改或撤销共享 N 份的公开写接口。不能虚构此类接口或将查询成功当作共享成功。

官方支持后台设置被授权企业、有效期、最大可用数、修改和取消共享。应用自动共享是另一项明确配置：企业授权包含 `signtask_init`，且应用账户启用自动共享时，才有 `bill-account-usage-share` 结果回调。该回调的成功结果不携带商签通订单的 N 份分配凭据，不能替代按订单控制份数。

当前已核验应用 `00005270` 为企业自建应用。其官方指引针对接入方及关联分子公司；商签通面向独立注册企业的统一付费场景还需核实第三方平台适用的账户共享、应用用户能力及现有采购套餐可用范围。不能在未核实能力时直接向所有授权用户开放无限共享，也不能擅自改合同双方主体来规避计费归属。

## 接入落地条件

2026-10-24 沿用户指定的 5.1 在线文档重新检查业务接口和接入指南，确认还有更直接的官方方案：**平台发起但不参与签署**。此前把逐企业分配服务商共享 N 份当作唯一方案过于狭窄。`initiator` 是任务发起方及扣费主体，`actors` 是实际签署方，两者并不要求重合。

可采用以下任一完整交付方式：

1. **平台统一发起、实际企业签署（优先核对）**。创建请求的 `initiator` 为云域，`actors` 保持真实供需双方；云域不加入签署方，也不写成合同当事人。商签通通过本地付费账本控制每家企业可发起 N 份，服务商向云域扣量。此路径不依赖逐企业转移共享份数的写 API。官方第三方应用模式一明确支持此场景，但当前自建应用能否启用该平台模式及相关权益仍需核实，不能仅凭接口参数通用就断言已具备权限。实现需完整处理新任务发起身份的冻结、创建、查询、原任务恢复、撤销、作废、文件访问及通知身份；历史由企业发起的任务保留原身份，不能随配置切换而改绑。
2. 保留客户企业作为服务商发起方，由法大大提供正式支持的共享分配写 API，可按稳定企业标识设置累计最大可用数、有效期和幂等键，并可查询结果、限制来源和撤销。支付核实后以持久交付记录执行，失败重试保留已付款事实；仅确认共享生效后标为签署可用。当前公开文档未找到该写 API。
3. 确认平台应用专用账户的自动共享只能通过商签通服务端消费，企业不能从官网或其他应用绕过商签通的 N 份账本消耗云域份数。在这个可验证的隔离前提下，法大大负责底层共享，商签通现有账本负责按企业精确限额，并补接共享结果及可用状态查询。

如果保留客户企业作为发起方且只能通过官网给每家企业手工共享，人工处理可以作为临时交付方式，不能宣称已实现付款后自动分配。不能把这个限制扩大解释成平台统一采购、自动按企业限额整体无法实现。单纯开启一个无限共享开关也不能满足本需求。

## 给法大大的具体确认问题

> 商签通平台所属企业河北云域科技有限公司，应用 00005270，目前为自建应用，已购 4000 份有效签署用量。业务为其他独立企业在商签通付款购买 N 份，由云域总采购量提供底层签署。优先拟采用《第三方应用集成指引》模式一的“平台方发起但不参与签署”：initiator 为云域，actors 为真实供需双方，平台本地按购买份数限制发起。请确认当前应用是否可使用该模式、是否需调整应用类型、现有合同和 4000 份是否适用及是否另有必须启用的能力。若要求保留客户企业为 initiator，请提供正式按企业分配共享额度的写 API，或明确应用专用账户自动共享的消费来源限制，防止绕过商签通本地份数继续消费。不得仅以云域自身 availableNum=4000 代替验证实际交付链路。

本次未更改线上计费、共享授权、支付订单或真实合同，未发起购买或签署。已确认存在官方平台统一发起方案，当前应用的启用条件尚未取得确认，完整自动交付尚未实现。
