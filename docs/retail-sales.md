# 零售客户与销售单

首页供应商视角使用“合作企业 / 零售”分区。零售客户不需要平台注册、企业认证、合作绑定或合同。客户和单据属于当前公司，跨公司 ID 无法查看、编辑、确认或导出。

## 金额口径

- 合作销售只计入 `business_document` 中未删除且状态为 `ACKNOWLEDGED` 或 `INBOUNDED` 的销售单。金额为商品和费用明细合计，每张单据只计一次。
- 零售只计入 `retail_document` 中状态为 `CONFIRMED` 的销售单。
- 首页按单据业务日期统计今年、本月或近 12 个月，销售总额包含合作销售和零售；退货金额另列，净销售额为销售总额减退货额。
- 合同约定金额不计入销售额。合同列表使用合同下销售单累计金额排序，先对全部符合可见性及状态筛选的合同排序，再分页。相同金额保留最近合同在前。
- 合同列表及详情同时显示合同金额与销售单累计金额。合作企业和零售客户金额分别统计，不按同名客户合并。

## 单据和库存

客户名称和类型必填；联系人、电话、收货地址、开票抬头、税号与备注选填。

零售单据先保存草稿，由本公司确认后生效，无需对方确认。创建请求按公司与 `requestId` 复用单据，网络失败后再次提交会更新同一草稿的内容，避免确认旧价格；已生效单据不再修改。确认和库存处理锁定单据，重复操作不会重复计账或改动库存。草稿可编辑或删除，已生效单据只读。编辑草稿刷新客户快照，生效单据保留原客户信息。

退货必须关联同一客户、同一公司的已生效销售单；商品、规格、单位及原单价由后端从原单带入。支持部分、分次退货。本次金额为累计退货数量乘原价后按分舍入，再减去已退金额，避免累计多退或少退金额。确认时锁定原销售单，再校验已确认退货数量与金额；其他退货改变尾差时，需要刷新草稿后确认。草稿不占用可退数量。退货原因必填，退款不作为退货金额自动支付。

销售出库及退货入库可在确认时处理，也可在单据详情后续处理。出库检查库存并记录库存成本；退货入库沿用原出库成本。原销售单尚未出库时，退货可先确认，但需完成原单出库后再办理退货入库。费用明细不影响库存。库存不足或任一商品处理失败时，整笔事务回滚。

客户查看沿用 `contract_view`、`order_create`、`reconciliation` 或 `invoice_view`；客户维护、单据编辑及确认需要 `order_create`；库存处理需要 `inventory_receive`。权限仍以服务端为准。

## 接口及上线

新增路由 `/api/retail/**` 归属交易服务。包含客户列表/详情/维护、客户单据分页、草稿创建/编辑/删除、单据确认、库存处理与 PDF 数据导出。

当前三进程环境使用 `Jenkinsfile.core`，按以下顺序发布：

1. `ACTION=deploy`、`SERVICE=business`：更新合同、交易、结算和文件模块。启动时 Flyway 自动执行 `db/business/V3__retail_customers_and_documents.sql`，创建三张零售表。
2. `ACTION=deploy`、`SERVICE=gateway`：开放新增的 `/api/retail/**` 路由。
3. 上传、审核并发布小程序。

本次无需发布 `identity`。现有 core 业务库不要手工执行旧单库的 V38；V38 仅用于仍使用 `sql/mysql` 迁移目录的旧单库。六服务环境的交易库使用 `db/owned/trade/V3__retail_customers_and_documents.sql`。

迁移仅新增零售表，已部署的 V1、V2 校验和保持不变，不将历史合同金额转换为销售金额。旧首页金额缓存升级为 v2，避免继续展示合同口径的缓存。离线分库工具要求旧单库已完成 V38；六库合并工具要求交易库已完成 owned V3。
