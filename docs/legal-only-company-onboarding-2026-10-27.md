# 仅法人本人首次入驻开关

> 后续发布范围与按需签署待办见[法人入驻与签署准备交付](legal-onboarding-signing-readiness-2026-10-27.md)。本文下方“未发布、未开启”描述的是本次会话的第一阶段；后续已安排开启线上配置并整体发布后端，前端由用户自行发布。

## 配置

`tradepass.fadada.legal-representative-only-onboarding-enabled` 默认 `false`。示例见 [Nacos 配置片段](../deploy/server/nacos/fadada-onboarding.example.yml)。

```yaml
tradepass:
  fadada:
    legal-representative-only-onboarding-enabled: false
```

开启时将值改为 `true`，合并到 `TRADEPASS_CORE` 分组现有 `tradepass-identity.yaml` 的 `tradepass.fadada` 节点。不要用片段覆盖整份配置；无需迁移数据库。应在配置刷新或重新启动 identity 后读取 `GET /api/ca/config`，确认 `legalOnlyOnboardingEnabled=true`。修改代码后需先发布 identity 与小程序；业务合并进程应同步构建以验证共享组件兼容性。源码与配置示例均保持默认关闭，本次未改线上开关。

## 开启行为

- 填写并保存企业资料仍只生成待入驻记录和候选申请，不授予正式企业权限。
- 首次入驻的企业认证链接指定 `corpIdentInfo.corpIdentMethod=["legalRepFace"]`，由法人本人在官方页面认证。
- 后端须取得具文档化个人标识语义的 `operatorType=legal_rep`、`operatorId`，核实其与申请人当前有效实名账号一致，并检查企业主体、实名、授权和姓名。姓名一致、企业认证完成、超管授权成功均不能单独放行。
- 原认证人为代理人、缺少可靠法人身份或不是当前申请人时，保留待核验，不开通 ADMIN 或 LEGAL，不完成租户初始化。
- 开启时，模拟认证不能作为法人本人核验依据；关闭后原有模拟测试流程保留。
- 已经正式开通的企业继续允许有权管理员补充资源授权，不重做首次入驻，不批量改变既有成员。
- `GET /api/ca/config` 在保留 `mockEnabled` 的同时返回 `legalOnlyOnboardingEnabled`。小程序仅据此显示引导；准入始终由服务端判断。

关闭后恢复原有合法法人/经办人入驻规则；已经阻止的申请须再次同步，修改配置本身不会直接批准申请。

## 服务商边界

[获取企业授权链接](https://dev.fadada.com/api-doc/CGKNKJZFM5/77KS5R59TERABQH9/5-1)支持指定法人刷脸方式，但已有法大大认证企业走超管授权流程，文档没有承诺强制重新法人刷脸。首次到商签通注册不等于首次在法大大认证。

5.1 SDK 经办人扩展字段非空时也尝试独立 5.0 身份查询；只在两版企业、时间、方式和经办字段一致时采纳具文档化语义的结果。失败或冲突保留未证明结果，严格入驻不接受旧全局信任开关替代可靠证据。这个补查修复解决原先“5.1 字段非空但不可信时不尝试 5.0”的条件缺口。

`corpNonEditableInfo` 只使用官方支持的企业名和信用代码字段，不把 `corpIdentMethod` 当作未文档化的不可修改字段。其他组织类型仅支持代理人认证时，不能通过本策略自动完成首次入驻。
