# 空用印授权与签署创建结果恢复

## 用印授权

`/seal/user/get-list` 的官方响应表将 `data` 标为可选。以前网关把成功响应中缺少 `sealInfos` 的情况统一作为“不完整”抛错，新加入企业、还没有任何印章使用权的成员因此可能无法进入首次授权页面。

成功响应中的空业务数据、缺少列表或空列表现在都表示“没有可复用的印章使用权”。管理员仍须具备本地成员管理和印章管理权限，随后由法大大官方页面确认用印授权。签署前依然必须查到指定印章 `enable` 且授权 `effective`；空结果不会取得签署权限。失败响应、空响应对象、重复或关键字段缺失的印章记录仍报错。

## 签署创建结果

已有实现会在外部创建响应丢失后保留独立提交的 `RESERVED/UNCERTAIN` 预占，以免重复创建和扣费，但原先没有主动查询这类任务的恢复路径，只会持续提示“上次签署创建结果待核实”。

签署预检和合同刷新现在可以只读核对之前的创建意图：

1. 必须已有原合同版本对应的预占、冻结快照和来源 SHA-256。普通刷新不创建新签署任务。
2. 有界分页读取原发起企业的任务，在本地按 `contract-{id}-v{version}` 精确匹配；必须确认完整读取且唯一匹配。没有匹配、多个匹配、查询失败或范围超限都继续保留原预占，不重发创建请求。
3. 对唯一结果再次读取任务详情，核对业务号、任务号、发起企业、两个企业参与方的 ID/真实企业主体/签署权限，以及唯一 `contract-doc` 文档的名称和原始文件 ID。
4. 每页最多 100 条、最多 20 页／2000 条；页码、总数、页数、记录数不一致或任务重复均停止核对。
5. 验证通过才确认原预占并恢复同一任务号、来源文件号及原冻结快照，不再生成 PDF 或占用新额度。已有任务不因更换企业默认印章而重新创建。

当前官方详情接口 `/sign-task/get-detail` 不返回完整参与方身份，故上述身份核验使用官方仍提供的兼容接口 `/sign-task/app/get-detail`（Java SDK `getDetail`）。普通状态同步仍使用当前接口。若兼容查询不可用或省略必要的参与方主体，则保留待核实状态，不凭姓名猜测关联。原始文件 ID 来自服务商记录；本次没有从服务商下载底稿重新计算 SHA-256。

明确收到 `212010` 时，网关改为受控的“电子签服务商签署额度不足，请联系平台补充”提示；预占独立保存该白名单原因，后续刷新与报价沿用，不输出服务商自由文本。对未知结果仍保留预占，不凭一次查询为空释放历史记录。

## 企业授权为什么又出现

企业实名、企业允许本应用访问组织/印章/签署数据、个人实名、具体成员用印权分别核验。现有新企业注册请求已经包含 `organization` 及全部签署所需范围，已授权完整时应复用；旧企业没有 `organization`、授权被撤回或服务商查到授权不完整时才要求企业超管补充。补范围页面由服务商统一显示“开通电子签”，不代表本地应该再次注册同名企业。成员加入商签通组织本身不等于已经获得电子印章使用权。

2026-10-24 使用用户提供的连接方式对当前服务器进行了只读核查，未更改生产数据、授权或任务：

- 反馈企业的数据库与服务商 `/corp/get` 均为已实名、已授权、启用，六项所需授权范围齐全；当前不需要重新开通企业电子签。
- 反馈成员本地为 ACTIVE 管理员；服务商成员已激活，个人实名主体和稳定成员标识均匹配。`/seal/user/get-list` 返回成功，但 `sealInfos: null`，确实没有有效用印权。这直接复现了原空列表被误判“不完整”的分支。
- 当天 09:54、10:26 两次合同创建都收到服务商错误码 `212010`。官方错误码说明为“订阅剩余可用量不足”，需平台在服务商计费模块核对实际发起主体的额度共享、分配及使用范围；该码不能证明总套餐余额耗尽，本地企业认证或再次授权不会解决额度配置问题。
- 对两笔当前合同版本，按发起企业查询并完整读取当前返回的两条服务商任务，逐条核对业务参考号，没有匹配任务。查询时没有重新发送创建请求，也没有直接清除历史待核实预占。
- 实测发现当前企业任务列表忽略 SDK 旧筛选字段 `transReferenceId`；当前官方请求表也未列出此筛选项。恢复查询需有界读取企业任务列表并在本地精确匹配参考号，不能把整家企业的任务总数当作匹配数。

线上取证进一步区分了“企业已授权”“成员未授印”和“平台服务商额度不足”三件事。用印实际开通仍需有管理权限的人确认；恢复签署还需要核对服务商可用量／共享配置，并按核对结果处理历史预占。本轮没有充值、授权、释放历史预占或部署。
